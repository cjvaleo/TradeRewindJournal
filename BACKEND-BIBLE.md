**Ten facts to internalize before writing any code**

1. **`index-6_22.html` is production** (`/`, `/account`, `/upgrade` all rewrite to it — `vercel.json:4,12,16`). `app.html` is a WIP rewrite: tracked in git and reachable at `/app.html`, but it omits `Authorization` headers on `/api/me` and `/api/billing/portal` (would 401), sends a `{scope}` payload to `/api/eod/render-card` that the deployed renderer rejects (400), and writes `journal:'default'` where production writes `'funded'`/`'paper'`. Copy its ideas, not its wiring.
2. **Auth to the API is always `Authorization: Bearer <supabase access_token>`** — no cookies (the only cookie in the system is the 10-minute OAuth CSRF nonce `rwd_oauth_n`).
3. **The `trades` table is a JSONB document store**: `id` is a *text* PK = `String(Date.now())` from the client; everything except `account_type` / `trading_day` / `journal` lives inside the `trade_data` JSONB blob. Some legacy rows have `trade_data` double-stringified — every reader must handle both.
4. **Tier truth is three `profiles` columns**: `is_pro && pro_active_until > now && pro_source ∈ {stripe_direct, discord_premium, discord_elite}`. Never trust `is_pro` alone; never gate on the legacy `profiles.plan`.
5. **Two tier vocabularies exist**: the server (`/api/me`) says `pro_direct|pro_premium|pro_elite|free`; the SPA internally says `direct|premium|elite|free`. Pick one and map at the boundary.
6. **Only one Stripe money path is live**: Pro Direct $19/mo via `/api/checkout/direct` (env `STRIPE_PRICE_DIRECT_ID`). Premium is granted *free* via the Trading Ark Discord role (Whop is never called — the Discord role is the truth); the $9 Stripe Premium and Elite are retired-but-defended code paths.
7. **Field gating** applies only to free users who signed up **on/after `2026-05-22T00:00:00Z`** (`TRIAL_GRANDFATHER_CUTOFF`, `index-6_22.html:21510`); the 7 gated field keys are `tags, notes, grade, emotion, confidence, tv_link, advanced` across two form scopes (`rw` log form, `cem` edit modal). Calendar/History lock 30 days after signup for those same users.
8. **RLS is the real security boundary** for everything the browser does with the anon key; the `/api` layer uses the service-role key and re-checks Pro itself (`requirePro`). Community endpoints exist precisely because cross-user trade reads would be denied by RLS… except co-members CAN read each other's `trades` rows directly (policy `trades_select_member`).
9. **`ANTHROPIC_API_KEY` is required by `/api/ark/*` but missing from `.env.example` and `.env.local`** — all three Ark endpoints degrade gracefully without it (deterministic fallbacks / silent skip).
10. **Cron + webhook are load-bearing**: `daily-role-check` (03:00 UTC) is what keeps Discord-granted Pro alive (35-day rolling window); the Stripe webhook writes tier state with a 7-day grace on every window. A new frontend never touches these — it only reads their output from `profiles`.

## 1.5 RLS assumptions the frontend relies on

The browser always runs with the **anon/publishable key**; RLS is the actual security boundary. The definitive policy set is in `supabase-avatar-migration.sql:63-528` (plus `rewind-migration.sql:174-194`, `confluences-migration.sql:87-129`, `broker-sync-waitlist-migration.sql:41-51`):

1. **profiles**: SELECT `using (true)` — public read (`supabase-avatar-migration.sql:72-74`). Required by: username search `.ilike` (`index-6_22.html:17993`), feed/rail avatar hydration (`13961`, `14533`, `14558`), invite-recipient name map (`28430`). INSERT/UPDATE own-row only (`auth.uid() = id`).
2. **trades**: SELECT own **or any community co-member's** (`trades_select_member` — `supabase-avatar-migration.sql:286-297`); INSERT/UPDATE/DELETE `auth.uid() = user_id`. The client deliberately sources `user_id` from the live JWT before upserting because "RLS keys on auth.uid() at row-check time" (`index-6_22.html:30958-30967`). The realtime `trades` subscription (`13909-13915`) also depends on the co-member SELECT policy.
3. **confluences / trade_confluences**: owner-`FOR ALL` policies; `trade_confluences` ownership derived via `EXISTS (… trades.user_id = auth.uid())` (`confluences-migration.sql:96-119`); `anon` role fully revoked (`:126-129`). `confluencesState.loadLibrary()` sends **no user filter at all** and relies purely on RLS (`index-6_22.html:20379, 20447-20450`).
4. **communities**: SELECT owner-or-member; INSERT `owner_id = auth.uid()`; UPDATE by owner **plus** a special `communities_join_via_invite` policy letting a user with a *pending invite* update the row iff the result contains their own UUID in `members[]` (`supabase-avatar-migration.sql:344-353`) — this is what makes `acceptCommInvite`'s member-array append work without service role; DELETE by owner.
5. **community_posts**: SELECT any member of the community; INSERT must be member and `user_id = auth.uid()`; UPDATE author-only; DELETE author **or community owner** (moderation — used by `removeMember`'s post purge, `index-6_22.html:17641`).
6. **community_post_likes / community_post_replies**: SELECT member-wide, INSERT/DELETE own row only (`supabase-avatar-migration.sql:449-500`).
7. **invites**: read/update/delete for `from_id` or `to_id`; insert only as `from_id = auth.uid()` (`:503-519`).
8. **user_settings**: `FOR ALL using/check (auth.uid() = user_id)` (`:521-528`).
9. **Service-role (RLS bypass) surfaces** — every write in `api/` uses `sbService()`: OAuth callback profile patch, Stripe webhook, both crons, all `api/rules/*`, `api/billing/*`, `api/checkout/direct`, `api/community/*` aggregations (cross-user trade reads that RLS would deny), `api/ark/*` (incl. `user_settings` debrief upsert), `api/insights/generate`, `api/broker-sync-waitlist`. `sbAnon()` on the server is used exclusively for `auth.getUser(token)` verification. Comment in `api/_lib/supabase.js:3-4`: "NEVER expose the service client to the browser."
10. **Locked tables**: `webhook_events` and `broker_sync_waitlist` have RLS enabled with **no** authenticated policies (service-role only — `rewind-migration.sql:185`, `broker-sync-waitlist-migration.sql:41-51`); `cancellation_reasons` allows only self-INSERT (`rewind-migration.sql:176-182`); `email_log` allows self-SELECT (`:190-194`).
11. `delete_my_account` must be SECURITY DEFINER in the DB to atomically cross-delete (definition not in repo — see §1.3).
12. **Not verifiable in repo**: `rules`/`rule_evaluations` owner-read policies for `authenticated` (required by app.html's direct fallbacks at `2651`, `2662`); the `journal`, `comm_data`, `to_username`, `likes_count`, `liked_by`, `note`, `discord_id/discord_username` columns have no migration files here — confirm them against the live schema before rebuilding.

## 4.1 Tier sources of truth (three parallel implementations)

### 4.1a In-app `getCurrentTier()` — `index-6_22.html:18143-18168` (the one the SPA actually uses)

Reads Supabase `profiles` directly (not `/api/me`). Never throws; every failure path returns the free default.

```js
async function getCurrentTier(){
  var safe = { tier: 'free', isActive: false, activeUntil: null };
  try {
    if (!_sb || !currentUser) return safe;
    var r = await _sb.from('profiles')
      .select('is_pro,pro_source,pro_active_until')
      .eq('id', currentUser.id).maybeSingle();
    if (r.error || !r.data) return safe;
    var d = r.data;
    var untilMs = d.pro_active_until ? new Date(d.pro_active_until).getTime() : 0;
    var isActive = !!(d.is_pro && untilMs > Date.now());
    if (!isActive) return safe;
    var tier = ({ stripe_direct:'direct', discord_premium:'premium', discord_elite:'elite' })[d.pro_source] || 'free';
    if (tier === 'free') return safe;
    return { tier: tier, isActive: true, activeUntil: d.pro_active_until };
  } catch (e) { return safe; }
}
```

So a user is "Pro" iff **`profiles.is_pro` is truthy AND `profiles.pro_active_until` parses to a future date AND `pro_source` maps to a known tier**. In-app tier strings: `'free' | 'direct' | 'premium' | 'elite'`.

## 4.3 `getTrialStatus()` — `index-6_22.html:21519-21543`

Trial constant: `var TRIAL_GRANDFATHER_CUTOFF = '2026-05-22';` (`:21510`). Trial length: **30 days from account creation** (not from first use). No argument; reads globals. **Fails OPEN** on any uncertainty.

```js
function getTrialStatus(){
  // Paid tiers — no trial concept.
  if (typeof isFreeTier === 'function' && !isFreeTier())
    return { active:true, expired:false, grandfathered:false, days_remaining:null };
  var created = (typeof currentUser === 'object' && currentUser) ? currentUser.created_at : null; // Supabase auth user.created_at
  var signupMs = created ? Date.parse(created) : NaN;
  if (!Number.isFinite(signupMs))              // missing/garbage created_at → never lock out
    return { active:true, expired:false, grandfathered:true, days_remaining:null };
  if (signupMs < Date.parse(TRIAL_GRANDFATHER_CUTOFF + 'T00:00:00Z'))   // pre-cutoff signup
    return { active:true, expired:false, grandfathered:true, days_remaining:null };
  var daysSince = Math.floor((Date.now() - signupMs) / 86400000);
  var remaining = 30 - daysSince;
  return { active: remaining > 0, expired: remaining <= 0, grandfathered: false,
           days_remaining: Math.max(0, remaining) };
}
```

Return shape: `{ active: bool, expired: bool, grandfathered: bool, days_remaining: number|null }`. Dates compared: `Date.now()` vs `currentUser.created_at` (the **Supabase auth user object**, assigned at `:28485` in `onSignedIn`), and `created_at` vs `2026-05-22T00:00:00Z`. Day math is floor-of-ms; day 30 exactly ⇒ `remaining = 0` ⇒ expired.

## 4.4 `isGrandfathered()` — `index-6_22.html:21552-21560`

Same predicate factored out of `getTrialStatus` (single source for save-handler defense + form locks + read-only branch):

```js
function isGrandfathered(){
  if (typeof isFreeTier === 'function' && !isFreeTier()) return true;  // paid ⇒ treated as grandfathered
  var created = (typeof currentUser === 'object' && currentUser) ? currentUser.created_at : null;
  var signupMs = created ? Date.parse(created) : NaN;
  if (!Number.isFinite(signupMs)) return true;                          // missing → safe
  if (signupMs < Date.parse(TRIAL_GRANDFATHER_CUTOFF + 'T00:00:00Z')) return true;
  return false;
}
```

# 7. WIRING A NEW FRONTEND

The minimal ordered checklist to get a blank page authenticated and reading real trades, then layering on the rest. Every step is copy-paste-able against the live backend — nothing server-side needs to change.

## Phase A — blank page → authenticated → real trades (the critical path)

1. **Load the SDK + create the client.**
   ```html
   <script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script>
   <script>
     const sb = window.supabase.createClient(
       'https://efxjxmtjycldvovcbczg.supabase.co',
       'sb_publishable_F3g-zezPLXXQ6Khe0woNhg_n1V1FORM'   // public anon/publishable key (index-6_22.html:28280-28281)
     );
   </script>
   ```
   Defaults are fine (session persists in localStorage under `sb-efxjxmtjycldvovcbczg-auth-token`).

2. **Session boot + auth state.**
   ```js
   const { data:{ session } } = await sb.auth.getSession();
   if (session) onSignedIn(session.user); else showLogin();
   sb.auth.onAuthStateChange((event, s) => { if (event === 'SIGNED_OUT') { clearLocalCaches(); showLogin(); } });
   ```
   Sign-in is plain email/password: `sb.auth.signInWithPassword({email, password})` — require `data.session` to be non-null before proceeding (confirm-pending accounts return a user but no session). Signup: `sb.auth.signUp({email, password, options:{data:{display_name, username}}})`.

3. **Load the profile** (create it on first login if missing — production upserts `{id, display_name, email, username, initials, color, plan:'free'}`, `index-6_22.html:30808-30818`):
   ```js
   const { data: profile } = await sb.from('profiles').select('*').eq('id', user.id).maybeSingle();
   ```

4. **Read real trades.**
   ```js
   const { data: rows } = await sb.from('trades')
     .select('*').eq('user_id', user.id)
     .eq('journal', 'funded')                      // production journals: 'funded' | 'paper'
     .order('created_at', { ascending: false });
   const trades = rows.map(r => {
     let td = r.trade_data;
     if (typeof td === 'string') { try { td = JSON.parse(td); } catch { td = null; } }  // legacy double-stringify
     if (td && typeof td === 'string') { try { td = JSON.parse(td); } catch {} }        // some rows need two passes
     return td && { ...td, account_type: r.account_type ?? td.account_type, trading_day: r.trading_day ?? td.trading_day };
   }).filter(Boolean);
   ```
   RLS guarantees you only get your own rows (plus community co-members' if you query other user_ids). **You are now a working journal-reader frontend.** Everything below is incremental.

5. **Resolve tier** (needed before rendering any gated surface):
   ```js
   async function getCurrentTier(){                      // mirror of index-6_22.html:18143
     const { data: d } = await sb.from('profiles')
       .select('is_pro,pro_source,pro_active_until').eq('id', user.id).maybeSingle();
     const active = !!(d?.is_pro && new Date(d.pro_active_until).getTime() > Date.now());
     const tier = active ? ({stripe_direct:'direct', discord_premium:'premium', discord_elite:'elite'})[d.pro_source] : null;
     return tier ? { tier, isActive:true, activeUntil:d.pro_active_until } : { tier:'free', isActive:false, activeUntil:null };
   }
   window._userTier = await getCurrentTier();
   ```
   For billing UI, prefer `GET /api/me` (authoritative, includes `hasDiscord`/`hasStripe`) with the Bearer pattern from step 6.

6. **The API fetch helper** — every `/api/*` call uses this exact shape:
   ```js
   async function api(path, opts = {}) {
     const { data:{ session } } = await sb.auth.getSession();
     return fetch(path, { ...opts, headers: {
       'Content-Type': 'application/json',
       'Authorization': 'Bearer ' + session.access_token,
       ...(opts.headers||{}) }});
   }
   ```

## Phase B — writing trades

7. **Port `js/tradingDay.js` as-is** (or `<script src>` it) — `trading_day` must be computed with the ET trading-day rules (`TradingDay.getTradingDay(ms)`), not the calendar date.
8. **Save = upsert** (mirror of `saveTradeToSupa`, `index-6_22.html:30955`):
   ```js
   const { data:{ session } } = await sb.auth.getSession();   // user_id MUST come from the live JWT (RLS)
   await sb.from('trades').upsert({
     id: String(trade.id),                    // Date.now() at creation; reuse on edit
     user_id: session.user.id,
     trade_data: trade,                       // plain object — never pre-stringify
     account_type: ['paper','eval','funded','live'].includes(trade.account_type) ? trade.account_type : null,
     trading_day: TradingDay.getTradingDay(+trade.id) || trade.date || null,
     journal: 'funded',
     updated_at: new Date().toISOString()
   }, { onConflict: 'id' });
   ```
   Delete: `sb.from('trades').delete().eq('id', String(id)).eq('user_id', user.id)` then cascade `sb.from('community_posts').delete().like('id', 'trade_'+id+'_%')` (a DB trigger also does this server-side).
9. **Confluences (tags):** manage the user library in `confluences` (`select('id,name').is('archived_at', null)` — no user filter, RLS scopes it), and persist per-trade links with DELETE-then-INSERT into `trade_confluences` `{trade_id, confluence_id, timeframe, position}` — but **only after** the `trades` upsert has resolved (FK parent must exist).
